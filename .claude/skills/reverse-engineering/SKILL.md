# Reverse-engineering game.exe

## 1. Find and read code (Ghidra, headless)

Start with the whole program decompiled once, with d2d's names on what
it ports: `tools/ghidra/decompile.sh` (a minute, after `import.sh`), then
`tools/ghidra/fn.py <addr>...` prints functions from it. A `/* d2d
verified: ... */` note above a function says where d2d ports or checks it;
a callee named `d2d_<file>_<function>` is already ported. A d2d function
gets its name there when the comment right above it cites one `FUN_`.
A function you traced that no d2d function is named after (a getter, a
SetFont, a table walker): add a row to `docs/research/re/names.tsv`
(address order; the name, the evidence) and it's `d2d_<name>` next run.
`tools/ghidra/calls.py <from> --to <addr>` lists the call paths from one
function to another in code order: what state (a font, a mode) is current
when something draws or runs.

Project: `tools/ghidra/project` (make it with `tools/ghidra/import.sh`).
Run one analyzeHeadless at a time (the project lock); chain several
`-postScript` calls in one run instead:

```
H=${GHIDRA_INSTALL_DIR:+$GHIDRA_INSTALL_DIR/support/analyzeHeadless}; H=${H:-$(command -v ghidra-analyzeHeadless || command -v analyzeHeadless || find /opt/homebrew/Cellar/ghidra -name analyzeHeadless -type f | head -1)}
$H tools/ghidra/project D2Decomp -process game.exe -noanalysis -readOnly -scriptPath tools/ghidra/scripts \
  -postScript DecompileAt out.c 00675360 006750f0 \
  -postScript Disasm 00612280 006122f0 out.txt \
  -postScript XrefsTo 006e681c xrefs.txt
```

- `DecompileAt <out.c> <addr>...` works on function starts only.
- `Disasm <start> <end> <out>`: the decompiler drops fastcall ECX/EDX args
  and `RET n` counts, so read the asm for calling conventions.
  `CallArgs.java` recovers them at call sites.
- `XrefsTo <addr> <out>` / `XrefsRange` show who calls or indexes something.
  Strings live in `docs/research/re/game-strings.tsv` and functions in
  `game-functions.tsv`, so grep those first.
- What d2d already knows about a function: `git grep -n 0057c6c0` (docs,
  code, oracles), or its `refs` in `build/gaps/functions.tsv`
  (`python3 tools/gaps.py`). That file is sorted by address, so a range
  is one awk: `awk -F'\t' '$1 >= "0057c000" && $1 < "0057d000"' build/gaps/functions.tsv`
  lists every function there, its status and where it's written up.
  Don't read a long research doc whole: grep it by address or heading. Struct fields are in
  `docs/research/re/structs.tsv`.
- Use `-process` on an imported program; `-import` re-imports and
  re-analyses it (about a minute). The TSVs are regenerated by
  `tools/ghidra/import.sh` (`ExportOverview` + `ExportCalls`); commit them
  when they change, except `game-strings.tsv` (game.exe's own bytes, kept
  local; see LEGAL.md).
- `game-calls.tsv` has every caller → callee; `tools/gaps.py` turns it
  into the gap map (status per function, the frontier, by module).
- Source file names in asserts (`.\DRLG\Drlg.cpp`) show which module a
  function belongs to.

## 2. Prove it (tools/emu, unicorn)

Don't claim "matches game.exe" from reading alone. Run game.exe's own code
on the same input and diff:

```
cd tools/emu && uv sync
uv run python -c "import emu; e = emu.Emu(); print(e.call(0x45c3e0, ecx=seed_ptr, edx=100))"
```

- A pure function: `Emu()` then `call(addr, *stack, ecx=, edx=)`.
- Anything that needs data tables: `emu.serve_files(e); e.crt_init();
  e.call(0x619300, 0, 1, 1)` loads every excel table plus the preset/LvlSub
  DS1s from the MPQs. `drlg.boot()` does exactly this.
- Struct fields by name: `e.view("unit", u).mode = 3`, from
  `docs/research/re/structs.tsv` (one row per field, with the line that
  shows it). Add the row instead of writing a bare `e.w32(u + 0x10, 3)`.
- Reuse a harness: `life_apply.Game(real={addr})` hooks damage and stats
  side effects and runs `addr` for real; `e.stub(0, {addr: nstack})` hooks
  the rest.
- An unstubbed import stops the run with its name and a stack. Add a
  `w_<Name>` returning `(eax, stdcall argc)` to `emu.py`, or `e.hook(addr,
  fn, nstack)` to cut off a subsystem you don't care about.
- CI has no game.exe: freeze the oracle's output as `tests/<name>_cases.inc`
  (its first line names the script that made it) and have the test read
  it, so CI checks d2d against game.exe's answers (`tests/overlay_cases.inc`).
- Pair every oracle with a small C++ dump tool (like `tools/drlg-dump`)
  that prints the same text, then `diff`. Sweep many seeds or inputs,
  because one match proves little.

Existing oracle: `tools/emu/drlg.py` for level generation (act, level
records, outdoor cell grids, room list and room seeds).

## 3. Write it down

- Findings go in `docs/research/re/<subsystem>.md`: addresses, struct
  offsets, tables, and the algorithm in prose. Raw decompiled `.c` stays
  out of git.
- The port goes in `components/<name>` with a test in `tests/`. Leave
  `ponytail:` notes on known gaps.
- Python tools are uv projects (`pyproject.toml` + `.venv`), never system
  pip.
